# Synthetic Demo Dataset — What It Is and Isn't

Generated by `backend/app/synthetic/generator.py` and loaded with
`python -m app.synthetic.cli`. Every asset/organization name it creates
says "(Synthetic Demo)" or "SYNTHETIC" explicitly, on purpose, so it can
never be mistaken for real plant data downstream.

## What it represents

Three fictional assets (a pump, a compressor, a conveyor motor) with 2–3
sensors each, ~5-minute sampling cadence, generated over a configurable
window (default 21 days). Each sensor's series combines:

- a baseline value with daily (24h) seasonality
- Gaussian noise
- a slow linear drift on one sensor (`PUMP-07/bearing_temp_de`), simulating
  gradual wear
- occasional sudden spikes/step-changes (probability-driven, deterministic
  under a fixed seed)
- randomly dropped individual readings (missing data)
- one guaranteed contiguous outage window per sensor (a real data gap, not
  just scattered dropouts, so the gap detector always has something to find)
- at least one spike in the most recent 15% of every spiking sensor's series
  (added at a fixed position when the random draws placed none there, without
  consuming random numbers, so a detector trained on the older history always
  has something to find in the newest data; every other value is unchanged)
- a handful of deliberately duplicated records (dedup demonstration)

## What it deliberately is NOT

- **Not real industrial telemetry.** The numeric ranges (temperatures,
  pressures, RPM) are plausible-looking but were not derived from any real
  equipment, dataset, or manufacturer spec.
- **Not a labeled fault dataset.** The spikes/step-changes are synthetic
  noise injected for the data-quality and (future) anomaly-detection
  pipeline to have something realistic to work with — they are not
  annotated as "this is a bearing failure" anywhere, and nothing in this
  codebase claims they represent one. No `Anomaly` rows are created by the
  generator; that table is populated only once real detection logic exists
  (a later phase).
- **Not validated against any real failure mode.** Anyone using this to
  demo or test predictive-maintenance concepts should treat the data as a
  plausible shape for exercising the pipeline, not as ground truth about
  how real pumps or compressors actually fail.

## Determinism

`generate_dataset(seed=42, ...)` uses `numpy.random.default_rng(seed)` —
not global random state — so the exact same seed always produces the exact
same records, byte for byte. This makes the demo reproducible across
machines and safe to re-run: the loader (`app/synthetic/cli.py`) is
idempotent, so re-running with the same seed re-ingests the same data and
the ingestion pipeline correctly reports it all as duplicates rather than
double-counting.

## Regenerating with different parameters

```bash
python -m app.synthetic.cli --seed 7 --days 45 --interval-seconds 60
```

A different seed produces a different (but still deterministic for that
seed) dataset; `--days` and `--interval-seconds` control history length and
sampling density.
